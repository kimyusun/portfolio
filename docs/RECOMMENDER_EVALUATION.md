# 추천 성능 평가 계획

## 왜 평가가 필요한가

현재 추천 로직은 해석 가능한 baseline ranking입니다. 따라서 “추천 점수식을 만들었다”에서 끝내기보다, 어떤 기준으로 더 좋아졌다고 말할 수 있는지 평가 방법을 함께 준비해야 합니다.

이 문서는 실제 사용자 로그가 부족한 현재 단계에서 가능한 평가와, 추후 서비스 로그가 쌓였을 때 확장할 평가 방향을 정리합니다.

## 현재 가능한 평가

현재는 실제 클릭/방문/스크랩 로그가 없으므로, 샘플 시나리오 기반 평가를 사용합니다.

- 입력: 추천 요청 payload
- 정답 신호: 사용자가 클릭하거나 스크랩했다고 가정한 장소 id
- 출력: 추천 결과의 ranking
- 평가: 정답 장소가 상위 K개 안에 들어오는지 확인

샘플 평가는 `dev/sample_payloads/reco_eval_cases.json`에 있습니다.

## 평가 지표

`scripts/evaluate_recommender.py`는 다음 지표를 계산합니다.

| 지표 | 의미 |
| --- | --- |
| `precision@K` | 상위 K개 추천 중 정답 장소의 비율 |
| `recall@K` | 전체 정답 장소 중 상위 K개 안에 들어온 비율 |
| `hitRate@K` | 상위 K개 안에 정답 장소가 하나라도 있으면 1 |
| `mrr@K` | 첫 번째 정답 장소가 얼마나 앞에 나왔는지 |
| `ndcg@K` | 정답의 중요도 점수를 고려한 ranking 품질 |

현재 샘플 데이터는 실제 성능을 증명하기 위한 데이터가 아니라, 평가 코드와 추천 정책이 연결되는지 확인하기 위한 smoke test 성격입니다.

## 실행 방법

```bash
python scripts/evaluate_recommender.py --cases dev/sample_payloads/reco_eval_cases.json --k 3
```

출력은 JSON 형태입니다.

```json
{
  "k": 3,
  "caseCount": 3,
  "aggregate": {
    "hitRate@3": 1.0,
    "mrr@3": 1.0,
    "ndcg@3": 1.0,
    "precision@3": 0.6666666667,
    "recall@3": 1.0
  }
}
```

샘플 데이터가 작고 의도적으로 만든 케이스이기 때문에, 이 숫자를 실제 서비스 성능으로 해석하면 안 됩니다.

## 실제 로그가 생겼을 때의 평가 방식

서비스 로그가 생기면 다음 신호를 정답 또는 약한 정답으로 사용할 수 있습니다.

- 추천 결과 클릭 여부
- 추천 장소의 메모 작성 여부
- 추천 장소 스크랩 여부
- 추천 후 일정 시간 안에 장소 상세 조회 여부
- 추천을 무시하고 다른 장소를 선택한 기록

그때는 사용자별, 감정별, 카테고리별로 평가를 나눠 보는 것이 좋습니다.

예시:

- `불안` 상태에서 긍정 장소 추천이 실제 클릭으로 이어졌는가
- `기쁨` 상태에서 기존 선호 카테고리 추천이 과도하게 반복되지는 않았는가
- `놀람` 상태에서 추천 결과가 너무 긍정 쪽으로 치우치지는 않았는가
- 신규 사용자와 기존 사용자의 추천 품질 차이가 있는가

## 다음 개선 방향

1. 실제 추천 로그 스키마를 정한다.
2. 클릭/스크랩/메모 작성 이벤트를 evaluation label로 변환한다.
3. 현재 휴리스틱 가중치를 grid search로 비교한다.
4. baseline과 개선안의 `NDCG@K`, `MRR@K`, `HitRate@K`를 비교한다.
5. 데이터가 충분해지면 learning-to-rank 모델 도입을 검토한다.

## 포트폴리오 설명 문장

> 추천 로직은 초기에는 해석 가능한 baseline ranking으로 구현했고, DB/MQ 없이도 샘플 payload 기반으로 정책을 검증할 수 있게 분리했다. 이후 추천 품질을 정량적으로 비교하기 위해 Precision@K, MRR@K, NDCG@K를 계산하는 오프라인 평가 스크립트를 추가했다. 현재 샘플 평가는 실제 서비스 성능을 증명하기 위한 것이 아니라, 평가 가능한 구조로 발전시킨 첫 단계다.
